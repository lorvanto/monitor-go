# 최초 활성화와 사용 현황 보고

[English](../en-US/USAGE_REPORTING.md) · [简体中文](../zh-CN/USAGE_REPORTING.md) · [日本語](../ja-JP/USAGE_REPORTING.md) · [한국어](../ko-KR/USAGE_REPORTING.md) · [繁體中文](../zh-TW/USAGE_REPORTING.md)

Monitor Go와 Monitor Console은 독립적인 저장소, 서비스 및 데이터베이스입니다. 소스와 데이터 디렉터리를 분리하세요. Monitor Go 설치에는 공개 저장소만 필요하며 비공개 Console 소스는 필요하지 않습니다. 표준 최초 설정에서는 구성된 Console에 연결해 온라인 활성화를 수행합니다. 이후 로그인, 모니터링 및 알림은 독립적으로 동작합니다.

표준 새 설치는 첫 로컬 관리자를 만들기 전에 온라인 활성화가 필요합니다. 설정 화면에 목적지(사전 지정된 Console 오리진이며, 실제 주소는 설치 또는 확인 화면에 표시), 통계 목적, 전송 항목 및 보고가 계속 켜져 있고 끄기 스위치가 없다는 규칙을 표시하며 고지 버전 `2`를 명시적으로 확인해야 합니다. 등록 성공 후 관리자를 만들고 지속적인 백그라운드 보고를 시작합니다. 로컬 사용자 이름, 표시 이름 및 비밀번호는 Console에 전송하지 않습니다. 등록 실패 시 관리자는 생성되지 않으며 연결 복구 후 같은 설치 ID로 재시도합니다. Console 계정이나 GitHub 로그인은 필요하지 않으며 개발자 계정에 자동으로 연결하지 않습니다.

보고가 켜진 기존 설치는 업그레이드 시 ID, 자격 증명, 계정 연결 및 과거 동의를 유지하며 새 동의를 임의로 만들지 않습니다. 이전 버전에서 꺼진 설치를 몰래 켜지 않습니다. `system:settings` 권한의 관리자가 현재 목적지, 항목 및 끌 수 없다는 규칙을 한 번 확인하고 등록에 성공해야 보고가 켜집니다. 등록 또는 로컬 트랜잭션이 실패하면 꺼진 상태를 유지합니다. 확인을 기다리는 동안에도 로컬 로그인, 모니터링 및 알림은 계속 동작합니다. 목적지를 바꾸면 이전 로컬 보고 ID를 지우고 새 목적지를 확인하기 전에는 전송하지 않습니다.

전송 항목은 임의 설치 ID, 버전, 운영체제, CPU 아키텍처, 배포 방식, 로그인한 사람이 화면을 조작한 UTC 날짜입니다. 로컬 계정 목록, 모니터링 대상, 호스트 이름/IP, 파일, 알림 본문, 비밀번호, 모니터링 키 또는 애플리케이션 키는 포함하지 않습니다. 설치 자격 증명은 등록과 인증에만 사용하며 화면에 표시하지 않습니다. Console 계정은 Monitor Go와 별개입니다. 로컬 계정은 사용자 이름과 표시 이름을 보관하며 선택적 GitHub 로그인에서는 검증된 GitHub ID, 사용자 이름 및 표시 이름을 별도로 보관합니다.

설치 등록과 활동 통계에는 계정 연결이 필요하지 않습니다. Console은 로컬 관리자 사용자 이름과 비밀번호로 로그인할 수 있으며 GitHub 로그인은 선택 사항입니다. Monitor Go 설치에는 OAuth 설정이 필요하지 않습니다.

계정을 선택적으로 연결하려면 로컬 Console 계정 또는 활성화된 GitHub 로그인으로 Monitor Console에 로그인하여 10분 동안 유효한 일회용 연결 코드를 생성하고 Monitor Go 보고 설정에 붙여넣습니다. 먼저 보고를 켜야 합니다. 연결 해제는 계정 연결만 제거하며 보고를 중지하지 않습니다. 콘솔에서도 자신의 설치 연결을 해제할 수 있습니다.

“마지막으로 동기화된 Console 계정”은 로컬에 저장된 정보입니다. Console에서 연결을 해제하면 다음 보고 성공 후 표시에 반영됩니다. 연결 장애나 기존 설치의 확인 대기 중에는 이전 계정이 남을 수 있습니다. “전송 상태 새로 고침”은 로컬 설정만 다시 읽으며 원격 동기화를 요청하지 않습니다.

활성화 후 독립 작업이 한 번 전송하고 이후 약 6시간마다 시간을 분산하여 보고합니다. 요청 제한 시간은 5초이며 리디렉션을 허용하지 않고 제한된 백오프로 재시도합니다. 대기 중 활동 날짜는 최대 7일입니다. 자동 새로 고침과 페이지 로드만으로 활동을 집계하지 않습니다. 일별 집계는 설치 단위 중복을 제거하며 사람 수를 나타내지 않습니다. 자체 보고 추정치이므로 신원이나 전체 설치 수의 증명이 아닙니다.

원격 등록 성공 후 로컬 설정이 실패하거나 취소되면 연결되지 않은 임의 설치 기록이 Console에 남을 수 있습니다. 재시도 시 같은 ID를 사용합니다. 따라서 등록 수는 완료된 설치 수나 실제 사용자 수와 같지 않습니다.

활성화 또는 확인 후 보고는 계속 켜지며 화면, API 및 배포 인수로 끌 수 없습니다. 끄기 요청은 HTTP 403을 반환합니다. Console 장애는 독립 백그라운드 작업의 지연 재시도로 처리하며 로그인, 모니터링 및 알림을 차단하지 않습니다. 일별 기록은 90일, 보고가 없는 설치는 365일 후 삭제됩니다. 이후 보고로 다시 등록할 수 있으나 계정은 다시 연결해야 합니다. 계정 연결을 해제해도 보고는 중지되지 않으며 수신된 이력도 삭제되지 않습니다.

HTTPS가 필요하며 숫자 루프백 HTTP는 로컬 통합 테스트에만 허용됩니다. 컨테이너 루프백은 자신을 가리키므로 별도 컨테이너에는 실제 HTTPS 주소를 사용하세요. 자격 증명, 데이터와 백업을 Git에 저장하지 마세요. 프록시 로그에 OAuth 쿼리, 전체 원본 IP나 자격 증명을 남기지 마세요.

데이터베이스는 계속 스키마 10을 사용합니다. 고지 버전 `2`는 기존 고지 버전, 동의 시각 및 활성화 시각 필드에 지속 보고 규칙의 확인을 기록하며 과거 동의를 다시 쓰지 않습니다. 업그레이드 전 전체 데이터 디렉터리를 백업하고 롤백 시 해당 전체 백업을 복원하세요. ID는 데이터와 함께 유지되며 복제하면 통계가 합쳐질 수 있습니다. 확인하지 않은 기존 설치 및 연결할 수 없는 클라이언트를 포함한 완전한 설치 수를 집계하지는 못합니다.

`MONITOR_CONSOLE_URL`을 설정하지 않으면 네이티브 실행 파일과 Compose는 사전 지정된 Console 오리진을 사용합니다. 실제 주소는 설치 또는 확인 화면에서 확인하세요. 다른 HTTPS 오리진으로 목적지를 바꿀 수 있으며 네이티브 `-console-url` 인수가 우선합니다. 비어 있거나 공백만 있는 목적지는 환경 변수로 지정해도 잘못된 구성으로 간주되어 표준 CLI가 시작을 거부합니다. 보고를 끄거나 활성화를 우회할 수 없습니다. 버전 조회와 백업 명령은 활성화 구성이 필요하지 않습니다.

표준 CLI와 Compose는 활성화 및 보고가 필수입니다. 기존 `-require-activation=false`와 `MONITOR_REQUIRE_ACTIVATION=false` 설정은 구성 오류로 거부되며 더 이상 지원하지 않습니다. `true`는 호환성을 위해 허용합니다. 오프라인 설치 또는 보고 끄기 인수는 지원하지 않습니다. 접근 가능한 HTTPS Console 주소를 설정하세요. 비어 있거나 공백만 있는 목적지는 시작 시 구성 오류로 거부되며 활성화를 건너뛸 수 없습니다. Console URL 인수는 해당 환경 변수보다 우선합니다. activation=false 설정은 true 인수를 추가해도 유효해지지 않습니다.

```sh
./bin/monitor -data data -listen 127.0.0.1:5080
```

`MONITOR_CONSOLE_URL` / `-console-url`; `MONITOR_REQUIRE_ACTIVATION` / `-require-activation`; `MONITOR_DEPLOYMENT=native|docker` / `-deployment`.

네이티브 실행 파일의 기본값은 `native`이며 Docker 이미지와 Compose는 자동으로 `docker`를 설정합니다.
